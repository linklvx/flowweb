1. 结论与执行决定

结论：不建议按 Y1c v1 原样实施。保留 Yjs + Hocuspocus、PostgreSQL 权威持久化、单协作所有者和异步任务骨架，但必须重写载体并发协议、世代切换、exec 真源及撤销边界。

方案的问题不是“少了几个守卫”，而是将 CRDT 收敛、数据库提交、业务状态机和用户撤销混作同一种一致性。增加 SV 判断、重连闩锁或字段扫描，不能补上这些边界。当前最危险的设计包括：用不连续的序列水位过滤增量；声称 append 会让实际上未变的快照 CAS 失败；将执行序号放入可撤销的 exec；以同步 ACK 代替持久化证明；将编码重放当成历史重建。

本报告直接确定以下目标，不保留待用户裁定项：

  1. Yjs 负责用户共同编辑的画布内容，PG 负责执行、产物、资金、存储配额和审计事实。 exec 从用户可写文档中移出，以 PG 运行态读模型与可靠追赶协议呈现。
  2. 快照版本与增量进度分离。 使用每项目、每世代事务内分配的连续 appendSeq；快照包含 generation；压缩采用事务外重放与短事务发布，CAS 比对世代和快照指针，不与正常 append 争胜。
  3. 世代来自已有项目元数据接口。 先取得 generation/schema，再创建新 Y.Doc、缓存和 provider；服务端仍执行认证、装载及写入三层 fencing。取消“末知 g + 首连故意失败”的主流程。
  4. 同代压缩不换世代；真正重建必须导出类型化可见内容并创建全新 CRDT 身份。 旧字节流不得直接合并进新世代。
  5. 同步完成不等于保存完成。 引入同连接有序保存屏障，只有 PG 提交完成才确认“已保存”。常规 GC 不靠销毁并重建客户端文档。
  6. 删除持久字段与替换全部读者在同一发布单元完成。 Y2 的最低限度投影合成和 Y4 的现有富文本绑定必须前移，不能把破坏性变更先上线、读侧以后再补。
  7. 现在没有用户数据：直接建设 v4 schema，一次部署 api/web，开发库重建。 不建设 v3 兼容读写、旧 spool 收养、存量回填或回退垫片；本报告不实际执行重置。

1.1 单人团队与多人团队的统一模型

单人团队不是另一个产品架构。两者共用同一 Y.Doc 内容模型、持久化、权限与执行协议，区别只在 presence 的人数优化。一个用户打开两标签页仍是两个副本，必须同步内容，但不必对本人广播远端光标。不能为单人绕过保存屏障、配额或 PG 执行真源，也不应让单人承受无对端的额外同步等待。

1.2 证据范围

本次只读核对 repository、registry、persistence、spool、shrink、客户端缓存/provider、UndoManager、执行/产物投影、配额及相关 schema。固定依赖为 Yjs 13.6.32、Hocuspocus 4.6.0、BullMQ 5.75.1、Prisma 5.22.0；根 TypeScript 配置已开启 strict。

已执行两组无文件、无数据库的内存探针，验证 Yjs GC、并发嵌套创建和编码重放。未运行 PostgreSQL 集成测试、全量 verify、浏览器演练、迁移、部署或外部 AI 调用。 数据库交错反例属于可构造的风险证明，不冒充本环境实跑结果；后文性能数字为拟定验收门槛，不是实测容量结论。

2. 先纠正方案基线

先区分已完成能力与真正缺口，避免按旧行号重建已经存在的机制。

  • 获取 generation 无须新增请求。 apps/api/src/modules/project/project.service.ts:87-108 已在现有项目接口返回 collabGeneration、collabSchemaVersion、collabViewerUid，并注释零新往返。

  • PG 已存在执行代际和产物 outbox。 schema.prisma:1074-1102 已有 execSeq；:1156-1205 已有 NodeArtifact、ArtifactProjection。应延伸其闭环，不重建另一套竞争真源。
  • AI 对象键已有确定性基座。 artifact-commit.service.ts:53-56 已含 team/intentRow/execSeq/index，并追加内容哈希。剩余问题是物化身份、上传前记录与孤儿回收，不是所有路径仍靠 randomUUID。

2.2 路线图自身存在冲突

master 的 E42④ 已将 SV 支配性收敛为“对账哨兵，非 compact 放行判据”，Y1c v1 又引用旧 E20 把它恢复成三处主守卫。E62 的 stateSeq 也不应被解释为完整性证明。评审必须以当前机制和最终有效语义为准，不能只复制裁决表。

“CanvasDoc 空=无行或零增量”同样错误：零增量可能是含完整内容的已压缩项目。 当前开发重置按环境明确授权进行；未来空画布只能依据类型化可见态判定，不能凭增量行数删除。

3. 主要不足与风险等级

等级说明：P0 表示若进入正式环境，可直接破坏内容、业务顺序、资金或访问边界；P1 表示必须在相应能力上线前补齐；P2 表示可后置的维护优化。这里的 P0 不是声称已经发生生产事故。

3.1 P0：快照 CAS 与水位论证不成立

v1 的 append 更新 revision，但 compact 比对 currentRevision。append 没改 currentRevision，不会按方案所述使 CAS 条件失效。两 compact 同时 INSERT (projectId,R+1) 还可能先碰唯一冲突，根本到不了“0 行 CAS”分支。

更严重的是取消取号前项目锁后，用 seq > stateSeq 装载。反例：A 取 seq=10 未提交；B 取 11 并提交；compact 只看到 B，写 stateSeq=11；A 随后提交；装载永远过滤掉 A。GREATEST、RR 或 SV 都不证明 maxSeq 以下已经形成完整提交前缀。

现代码 canvas-doc-update.repository.ts:63-69 在 nextval 前取得项目锁，:123-145 在一个 RR 事务内读取全部残留增量，:260-286 按实际重放 ID 删除。原设计将现有保护拆掉，却没有提供等价证明。

3.2 P0：世代只在名称校验，缺少写入时 fencing

认证通过后可能马上遇到重建；已经加载的旧 Y.Doc、异步 store、spool replay 或在飞内部写仍可能晚到。文件名带 g 不足以保护 PG，尤其若回灌时把旧 payload 重新贴上“当前 generation”。

当前 append(projectId,update) 仅检查 lease owner（repository :53-69），没有 expectedGeneration/epoch；Snapshot 提案也没有 generation，却要求“每代 K=1”。应让每条数据从产生开始携不可变 g，并在真正落库的原子事务中验证。

3.3 P0：编码 identity 不等于历史重建，也不是故障修复

encodeStateAsUpdate 把现有 CRDT struct 身份和 DeleteSet 编码出来；应用到空文档不会自动产生新历史身份。内存探针确认 identity replay 的 SV 与原文档相等。因此它不能消灭 GC 壳、解决永久 pending 或隔离旧历史。

另一方面，当前 rebuildVacuumDoc 会创建新文档（registry :628-643），但克隆与等价性只覆盖有限类型，不能直接承接 Y.Text/Y.Array/Y.XmlFragment；:650-662 的 exec 键集合相等也不代表 exec 内容相等。真正重建必须按 manifest 类型导出并重建全部可见域。

3.4 P0：exec 自增与撤销形成第二真源

exec 删除后自增计数消失；undo 可能恢复旧 loading、旧 artifact 和旧序号；重建后计数又可能从 1 起步。迟到旧任务由此重新获得写入资格。现有 PG execSeq 恰是正确承载，不能在 Yjs 再做一个自增源。

applyWriteExecStatusToDoc 当前仍比对 attempts 而非 execSeq/intentId（collab-document.service.ts:307-325），也确有缺口。但正确修法不是换成“exec 内自增”。执行事实不能被用户内容撤销回滚。

3.5 P0：客户端 origin/静态门禁不构成服务端字段权限

编辑者可以手工构造二进制 Yjs update，写 exec、替换父 map 或携带删除集。客户端 canApplyIntent、TS manifest 和“只删不设”测试拦不住这种网络输入。

现 guardSyncFrame（registry :676-780）检查世代历史、帧、速率及配额，没有建立完整保护路径权限。Yjs origin 是本地 transaction 标记，远端由 provider/connection 重标，不是可信作者身份，也不是字段 ACL。因此首先应移走执行/资金事实，其余受保护结构在服务端应用前检查。

3.6 P0：同步 ACK 与 PG 保存之间存在崩溃窗口

Hocuspocus 4.6.0 MessageReceiver.ts:241-280 应用内存 update 后就发送 SyncStatus；数据库 store 是另一条去抖链。isSynced && !hasUnsyncedChanges 只能证明协议层已接收，不证明 PG 已提交。

若据此清 dirty、销毁文档或刷新，接着 collab 在 store 前被 kill，客户端已放弃唯一未持久化编辑。provider 注释使用“persisted”一词也不能替代实际服务端提交时序。

3.7 P0：存储确认存在误删完成资产的路径

storage-quota.service.ts:15-49 聚合 completed 用量后无锁检查；重复 confirm 将既有素材的字节再次相加，超限分支不先确认 pending，直接删除对象和 Media 行。并发 confirm 也可同时通过。

AI finalize 目前明确采用软 quota（artifact-commit.service.ts:23-24）。不能在付费外呼后临时调用现 assertOnConfirm，把成功产物删除。根修必须是外呼前原子预留、物化后结算、完成态幂等确认。

3.8 P1：Undo keep 回收方案破坏剩余撤销保障

截断数组确实未解 keep（canvasUndo.ts:38-43）。但只扣剩余 deletion 区间，不覆盖 redone 链、父容器及其他有效历史；对新 Y.Doc 重放时 keep 不序列化，剩余撤销依赖也可能被回收。

本次固定版本探针：保留删除内容 1051B；clear() 后仍 1051B；显式 tryGc 后 27B。说明“唯一回收路径=重建客户端 doc”不成立。tryGc 虽有导出，但涉及底层 store，应隔离为固定版本专用适配器，不能到处调用。

3.9 P1：Y.Text、嵌套创建和字段删除存在实施断层

两副本各自在同 key 创建 Y.Map/Y.Text，会竞争父 Item，最后只保留一支。本次两个独立 exec map 写 status/artifact 的探针，收敛后只剩 artifact。唯一函数不是唯一分布式创建者。

删除 data.fileId/status，却把图像完成判断、工作流素材、media refs 等读者留 Y2，会立刻造成“生成完成但界面 idle/素材消失”。这是缺实现，不是允许保留的兼容过渡。

3.10 P1：告警出口不能代替可执行恢复

“compact 连败三次→人工 identity 重建”无法修复因果缺失；若源已不完整，导出可见态只是固化缺失。先暂停 store 再要求 store drain，亦缺少维护专用通路。

当前 resident releaser 还存在结果丢失：residency :166-175 对单项目 await tryRelease 后未返回其结果。维护方必须拿到类型化 quiesce 成功/失败，不得把 undefined 当成功。强刷和断连不是事务屏障。

4. 确定的目标架构

以下设计将协作内容、业务事实与展示投影分开，同时保留统一团队权限模型。

4.1 三个平面，一个权限体系

内容平面： Y.Doc 内仅保留用户共同编辑的 nodes、edges、文本、配置、时间轴内容与引用；几何只存用户意图的绝对值，临时拖拽/hover/selection/progress 不落 doc。

业务平面： PG 保留 GenerationIntent、NodeArtifact/Media、资金账本、运行态修订号、配额、命令/审计。当前已有 ArtifactCommit/ArtifactProjection 必须作为唯一演进起点。

展示平面： 一个纯函数 projectCanvas(content,runtime,mediaFacts,ephemeral) 合成渲染 DTO。熟悉的 data.status/fileId 可以出现在 DTO，但不再成为持久化键。这是正常投影，不是根据旧版本分支的垫片。

数据流确定为：用户编辑 → 内容 CRDT/内容保存；用户执行请求 → PG 固化计划与 execSeq → worker → PG finalize/账本/outbox → runtime 读模型 → 展示合成。媒体尺寸等不可伪造事实来自 PG，不为了“doc 自足”再复制成用户可写权威字段。

自足性重新定义： 冷启动可从内容快照 + 授权运行态快照 + 媒体事实重建完整视图，无 socket.io 历史事件依赖。不要把“所有业务事实都塞进一个 Y.Doc”误称为自足。

4.2 权限与强业务不变量

网络信任边界在服务端，先鉴权、检查项目/团队 ACL，再解析和受理更新。客户端只可提交 manifest 中授权的叶子编辑；禁止未知根、父容器替换、无权创建/删除、非授权共享类型及引用越权。检查应覆盖二进制 struct 和 DeleteSet，无法解析父归属的延期内容不得被当作安全空更新。

节点/边创建、删除、重父级、跨记录引用和重要媒体绑定采用类型化命令，由项目 actor 串行验证与提交。命令在 shadow doc 上预演，落 PG 内容增量及必要的取消/退款观察事实后，才 apply 到 live doc 并广播；提交失败丢 shadow，提交后 apply 失败则 fence 并重载。commandId 幂等，不能重试时重复创建节点。

普通文本/几何仍直接 CRDT 编辑；乐观结构预览留本地 overlay，不把可能被服务端拒绝的结构先写入权威 Y.Doc。此设计明确取舍：离线文字和叶子编辑可保留；要求强约束的离线结构命令待上线提交，不承诺离线任意改图仍实时通过全局约束。

原始二进制拒绝不得逐字段过滤后继续同步，那会破坏 CRDT 因果。违规帧整体拒绝并给终态/错误原因，本地未获受理内容保留在独立恢复区，不与已承诺的服务器状态混淆。

4.3 撤销划分

  • 文本和普通叶子编辑使用 Y.UndoManager，按 origin/类型确定范围。
  • 结构命令以补偿命令撤销，重新检查 parent/edge/reference 不变量；原命令的前值由有界命令历史承载。
  • exec、资金、退款、Media 物化不进内容 UndoManager。撤销删除可以恢复节点，但不能恢复已退款产物为免费交付，也不能恢复旧 loading 为真状态。
  • 文本焦点内只由编辑器协作历史消费 Ctrl+Z；不让画布与 Tiptap 两个 UndoManager 同时处理一次按键。

这意味着原 E2 的 [nodes,edges,exec] 绑定和 E22 的 exec 自增必须改写。该偏离是在纠正真源边界，不是绕行补丁。

5. PG 载体与压缩协议

载体正确性由连续提交前缀、同代约束和短事务发布共同保证。

5.1 表与数字语义

目标模型如下，字段名可以映射现有实体，但语义不得混用：

  • CanvasDoc(projectId PK,generation,schemaVersion,lifecycle,currentSnapshotRev,appendSeq,ownerEpoch)：只保存小型头部。appendSeq 为本项目当前世代最后已提交序号；currentSnapshotRev 为不可变快照版本。
  • CanvasDocSnapshot(projectId,generation,snapshotRev,stateSeq,state,stateHash,schemaVersion,createdAt)：复合主键 (projectId,generation,snapshotRev)；stateSeq 是该快照覆盖的完整提交前缀。
  • CanvasDocUpdate(projectId,generation,seq,update,updateHash,createdAt)：主键 (projectId,generation,seq)；只追加。哈希用于字节校验/同代重复识别，不与业务命令幂等混为一谈。
  • 必要的保存屏障回执/命令 receipt 用独立唯一键留存；不能因为压缩删增量，就丢掉业务重试所需的提交证明。

所有长期序号用 BigInt，wire 显式十进制 string。snapshotRev 可采用 BigInt，避免 Int 溢出及 number 精度问题。指针使用复合关联或约束触发器保证只能指向同项目、同代快照；“不存在头行”和“存在头但指针悬空”必须分档。

不保留 CanvasDoc.stateSeq 的第二冗余真源；若为性能保留便利列，应明确只能在快照发布事务内同步，并有数据库一致性断言。

5.2 append：取号在锁内，提交前缀天然完整

短事务统一次序：稳定读取并锁住 CollabLease owner/epoch → 锁 CanvasDoc 行 → 检查 expectedGeneration、expectedEpoch、lifecycle → 去重 → appendSeq+1 → INSERT update → 更新 appendSeq → COMMIT。

不用全局 nextval 的数值大小推断提交顺序。 对同一 CanvasDoc 行，取号发生在行锁内，事务回滚连同计数回滚；后继事务获得锁时，前继已提交或回滚，因此形成每代完整前缀。

租约行采用可稳定 owner/epoch 的短 FOR SHARE 而非每个项目独占全局租约；takeover/修改必须使用冲突锁。KEY SHARE 不足以阻止普通列的 owner/epoch 修改。租约心跳、接管、维护、项目删除和内容写共享明确锁序，禁止持 PG 锁再等待 actor/inbox。

现有 funds 锁序 TeamBalance → GenerationIntent 保持。涉及内容与资金的复合命令，在项目 actor 先排程、刷前置内容，再按统一 DB 顺序加锁；不允许维护反向等待已持资金锁的 worker。

5.3 装载：RR + 前缀完整性，不靠 SV 猜丢行

只读 RR 事务读取 head 的 generation、appendSeq=N、快照指针 R；获取同代 Snapshot(R)，其 stateSeq=S；读取 S < seq <= N 全部增量，检查顺序连续及数量 N-S，校验字节哈希，再在事务外 apply。

S<=N、指针存在、前缀连续是结构完整性证据；SV/pending 是附加 CRDT 诊断。事务外重放失败必须拒载，不返回可编辑的半文档。读事务不需要 FOR UPDATE，因此不会把全量重放时间压在写锁上。

这里证明的是数据库按约定存下来的完整性，不是能发现从未被受理/持久化的客户端编辑。后者由保存屏障和本地持久化覆盖。

5.4 compact：事务外计算，短事务发布

  1. RR 获取快照 R 与完整增量前缀至 N，并拷贝数据，退出事务。
  2. 在有界后台任务/worker thread 中重放、编码、校验；不占用 WS 事件循环和 PG 行锁。
  3. 短事务按同一锁序检查 (generation,currentSnapshotRev=R,ownerEpoch)；允许当前 appendSeq 已大于 N。
  4. CAS 成功才插入 R+1 快照、指针指向 R+1、stateSeq=N，并删除实际重放的同代行集；任一步失败整体回滚。
  5. CAS 失败不留孤儿快照、不删增量；分类记录 conflict/not-owner/generation-changed/incomplete，后续重新计算。

append 不需要让 compact 失败：新到的 N+1 以后增量自然保留，由新快照之后继续装载。两个 compact 只允许一个发布；不得先 INSERT 撞唯一键再把所有错误折成正常 CAS miss。

普通同代编码必须保留 pendingDs 的编码语义，不声称 pendingStructs/pendingDs 为空能检测整行缺失。未解析因果数据不能在可见态重建中静默抛掉；连续不完整时停止破坏性维护，走明确恢复诊断。

5.5 保留与性能

生产起步：当前世代保留最近 2 个快照；最近 2 个已封存世代各留最终 1 个，共最多 4 个常规本地快照。更旧历史按明示策略删除或进入备份，不能“每代 K=1”无限积累。快照不可 UPDATE；DELETE 仅保留策略所有者执行。开发库当前无数据，不做历史归档迁移。

压缩最低机制必须随载体上线：事务外重放、显式超时、低并发后台调度、字节/行数触发、写放大与 bloat 观测。把这些全部留 Y6，将使新追加表只有形态收益而没有可靠运行机制。Y6 可承接分层归档、自动恢复与更复杂自适应。

6. 世代切换与客户端生命周期

换代必须同时隔离服务端在飞写与客户端仍在内存的旧历史。

6.1 获取 generation 的确定路径

复用现项目元数据响应，认证后返回 viewerUid、generation、schemaVersion、必要的协议版本。客户端检查 schema 匹配后，固定 {uid,pid,g,schema,sessionEpoch}，再创建 IDB、Y.Doc 和 provider project:<pid>#g<N>。

localStorage 只可作展示/提示，不作为当前 g 真源。服务器认证时再次查询/核验，装载时再核验，append 时最终核验，处理元数据获取与实际连接之间的 TOCTOU。

错误必须真正投递：4.6.0 ClientConnection 在 Auth catch 中只发 PermissionDenied(reason)，不自动把 Error.code 变成 socket close（:544-557）。采用已有 hardClose 机制主动关闭，并将认证拒因与 close 归入同一类型化映射。4410 触发重新取元数据并创建完整新会话，不只换 provider。 合法 generation 提示只能在登录/项目 ACL 通过后返回。

generation 频繁变化与网络故障不能混作“一次重连后永远 terminal”：同一目标世代限一次纠偏，目标真的改变可重新开始；设置退避与总次数预算，超预算明确维护中。

6.2 缓存隔离真正需要的操作

当前 terminal recovery :514-526 复用旧 doc，仅重建 provider。世代切换必须停止写入、清全部旧重试、完成本地未确认日志写入、拆卸 observer/UndoManager/cache writer/provider，再 destroy 旧 doc，创建新 doc。observer 回调及 in-flight promise 全检查 sessionEpoch。

不能清“该 pid 所有库”再假装正确性成立。多标签会阻塞删除，或另一标签已打开新代。隔离靠四维键与不可变会话，purge 只是卫生；只处理旧会话/旧代，保留未获 PG 确认内容到 detached 恢复区。二进制备份导入亦必须校验项目、世代及 schema；跨代只允许类型化导入，禁止 raw applyUpdate。

6.3 重建协议：先阻新生产者，再排空，不先禁 drain

维护状态机使用 PG lifecycle 和 maintenanceId，而非一串散落布尔：SERVING → QUIESCING → DRAINED → REBUILDING → SERVING。

确定步骤：

  1. 项目 actor 关闭新结构/叶子写受理与内部写者，暂停新任务 claim；已飞外部任务保留在 PG，完成事实继续落业务平面。
  2. 旧连接变只读，等待正在应用/写入操作结束。维护专用 drain 仍可运行，不能同时暂停它。
  3. flush pending、回灌当前代 spool 到 PG；确认 pending、spool、在飞 append/actor 作业均为零。失败返回类型化结果并保持封闭，不自动换代。
  4. 关闭旧连接并完成卸载，基于已提交一致快照导出 canonical 类型化可见态。
  5. 按 manifest 用全新 Y.Doc 创建 Y.Map/Y.Text/Y.Array/Y.XmlFragment；输出语义校验报告。不能复用已 integrated 的旧共享类型实例。
  6. 同一短事务封存旧代最终快照，写新代初始 Snapshot，generation+1、appendSeq=0、schema 设目标版本；旧代增量清理仅在其归档与覆盖证明成立后执行。
  7. 精确清旧代内存键，恢复受理；客户端 4410 后重新取元数据，打开新会话。
  8. maintenanceId 幂等、可观察、可继续；进程在任一步 kill 后，由持久状态决定继续/中止，不靠人工猜测执行到了哪一步。

schema 变化或恢复可使用同一机器。不完整源不能 identity 自动自愈：优先找完整存储/备份恢复；仅在明确标记“缺损救援、不是无损恢复”的工具中导出可见部分。快照回滚也通过创建更高 generation 承接旧快照，不把 generation 降回过去。

7. 内容模型、创建者和 Undo

文本合并、共享类型创建和撤销回收需要一体设计，不可各片独立猜测。

7.1 文本类型现在就分清

纯文本 prompt/普通文本采用 Y.Text，直接传编辑器 delta/splice；禁止每键 getHTML 或重新 diff 整串后覆盖。中文 IME composition、粘贴、选区、两端同位置插入必须独立验收。

现有 TextInputNode 的富文本采用 Y.XmlFragment + 与当前 Tiptap 2 系列匹配的 Collaboration 绑定，禁用 StarterKit 的本地 history；不要照抄在线最新版配置项到已固定的 2.10.0。格式化 HTML 仅用于渲染/导出，不作为合并真源。相关最小绑定从 Y4 前移，批注与高级富文本功能仍可留 Y4。

每种共享类型都有唯一创建责任和明确初始化时机：节点与 data/文本容器在结构创建命令中一次性创建，后续叶子写者只取得现有实例。不存在容器应拒绝/等待创建，不允许 client/server 双方 lazy-create 同一 key。

时间轴入 doc 必须同步迁走实际消费的 VideoProject.data 写/读，不能先放空根宣称迁移完成。cells 稳定 ID 应针对真正用户编排项；PG 衍生产物 cells 不重复变成 doc 第二真源。暂未迁移的功能只保留明确原真源，禁止双写。

7.2 Undo GC 的确定修法

固定版本的 bounded-undo 模块管理历史条数与字节预算，初始上限 100 项、4MiB 保留内容预算。预算在入栈前/后统一核算，不在任意 store 中操作数组。

退休项回收必须覆盖有效 undo、redo、redone 和必要祖先闭包；对于仍被当前有效历史保护的 struct 不释放 keep；redo 被新输入清空、clear、detach/destroy 都进入同一生命周期。release 后在非重入维护窗口，对待回收的精确 DeleteSet 调用固定版本 tryGc；自动化验证其不会回收活内容与剩余 undo 依赖。

只为项目现用的 UndoManager 和已引入的编辑器历史建立明确关系，不设计通用无限复杂引用计数框架。若未来新增编辑器管理器，必须先注册其保护范围再启用。

结构删除由补偿命令保存语义前值，不依赖保留整棵 Yjs 删除 struct。原“删 200 个 1KB 节点后完全回落”应改为：退休结构内容可回收、有效 100 项历史仍可恢复、GC 后字节不含退休负载。若测试仍保留 100 项完整删除内容，要求其字节归零本身不合理。

常规 GC 不销毁 provider/Y.Doc，不清剩余历史；generation 维护、项目切换或显式“清撤销历史”才是历史重置边界，并以 PG 保存屏障与本地写完成为前置。

7.3 语义 fixture，不要求随机 CRDT 字节逐位一致

fresh Y.Doc 会生成不同 clientID，XML/文本 struct 划分也受事务/创建顺序影响。重建 fixture 比对 canonical 可见语义、类型、稳定 ID、引用与排序，不能把“二进制逐位一致”作为一般迁移判据。

binary hash 用于验证同一已存快照未损坏；确定性种子 fixture 可另外比较字节，但不得为测试通过在生产强行固定 clientID。

8. exec、产物与退款可靠闭环

运行态以既有 PG 权威链演进，撤销不参与业务事实排序。

8.1 PG 唯一执行序与状态矩阵

保留现 PG execSeq，wire string。attemptId=intentId 表示用户请求分组；execSeq 表示新 claim/rearm 的执行代际；attempts 只表示该请求的免费重试次数。另用 eventVersion/runtimeRevision 表示同代 loading、done、error 等状态推进。

执行入口：未知 nodeId/零可执行节点显式拒；loading 拒新执行；done 在 execute-all 跳过，明确 regenerate 走新请求；error 重试按真实费用/额度规则，不从 doc 状态猜测。

当前态只有一个执行/产物视图，PG 保留有界历史。新的 execSeq 优先；同 execSeq 必须同身份、eventVersion 单调；终态不回退。artifactRevision 独立保护用户 replace/clear，不因旧任务晚到回滚。

8.2 延伸已有 outbox，不增加平行投影队列

将现 ArtifactProjection 演进为持久运行态事件/投影，loading、error、done 都在其业务状态事务内落 PG。既有 PG poller 可继续担当可靠 dispatcher；BullMQ 只调度重活或作为加速提示，不再成为第二张真源。若使用队列，jobId 用 eventId 或 intent+execSeq+eventVersion，且采用非冒号分隔符。

进程重启和 Redis 清空后，PG pending 可重新投递。claim 带 runId/leaseUntil，完成标记要同时验证 runId、期望状态和目标修订号。过期 worker 的 mark 不得把新 run 结果改坏。

v1 “kill 后 30 秒内 done”改为更准确验收：PG 已终态成功且产物已可交付的任务，collab 恢复后 30 秒内展示当前终态；materializing 必须展示真实物化中，不能为了达标伪造 done。 AI provider 完成、资金核销、对象物化和界面展示是不同状态。

stateless 仅发送可丢的 revision 提示/progress。冷启动和每次重连读取授权 runtime snapshot；先订阅提示再取快照，按 runtimeRevision 追赶，补齐订阅与快照之间竞态。不能以 execSeq 替代整体 runtimeRevision。

8.3 删除、undo 与退款

删除结构命令持久记录 deletion-observed，并将相关在飞执行标为不可节点交付。外部 provider 可能不能取消，结果进入明确 orphaned/discarded 状态，退款指向确切 execSeq 与原 settle ledger row。

现 rollbackDeliveryFailed(intentRowId,reason)（team-credit.service.ts:257-276）只按 intent 行与 status CAS；该行可能 rearm，新代资金被旧代迟到退款误命中。所有退款/释放/取消 API 补 expectedExecSeq 和 exact ledger identity，不以 mutable intent 当前值代替原凭据。

undo 恢复节点后只重新读取 PG 当前状态：已退款显示“已取消，需重新生成”；仍在飞且未取消可显示真实 loading；完成且未被撤销交付可展示其合法产物。禁止让 UndoManager 恢复幽灵 loading 或免费重跑已退款生成。

第三方 provider 不支持幂等时，不承诺跨 provider exactly-once。提交前记录 requestId、提交后保存 taskId；不确定成功的超时走 query-first/人工可见 UNKNOWN，不自动重复付费 submit。

9. 保存屏障与本地持久化

保存状态必须以可验证的提交证明为边界，不能由同步信号推断。

9.1 保存状态分成三档

UI 明示“本地修改/同步中”“服务器已接收但待保存”“已保存到服务器”。成功同步 ACK 只转第二档；PG 保存回执才转第三档。spool fsync 可报告“本机故障保护已写”，不能冒充 PG 保存完成。

9.2 复用同 WebSocket 的有序 marker

客户端先调用 provider 的公开 flushPendingUpdates()，再在同连接发送 save-barrier，含 nonce、sessionEpoch、generation 和本地 edit watermark。服务端在被 await 的 beforeHandleMessage 有序入口识别 marker，捕获此前所有已受理更新的项目 actor 前缀，等待该前缀进入 PG，再回 (nonce,g,committedSeq)。

不能在普通异步 onStateless 里随意 await 后再取水位：4.6.0 MessageReceiver :116-124 调 statelessCallback 时没有 await，marker 可能被后续更新超越或脱离会话。

回执只清 marker 之前的本地 dirty，后续输入仍脏；跨连接、旧 provider、旧 generation 的迟到 ACK 无效。连接曾拒帧则该屏障不可成功。断线后重发内容并用新 nonce，不复用旧屏障。

这不是另造版本握手通道，也不拿 SV 当保存证明。删除-only update 同样先经过 marker 序列，因此被覆盖。PG 正常批写仍可保留约 3 秒上界，但在屏障前不对用户宣布已保存；必要时保存/执行/离页触发提前 flush。

本地 IDB append 以事务 complete 为成功，关闭缓存实例前刷完日志；日志 GC 只删已经覆盖且已确认的记录。页面崩溃前尚未完成 IDB 的毫秒窗口单独披露，不能把浏览器缓存称为绝对零 RPO。

10. 存储配额、对象身份与审计

预留、物化、幂等和审计各有独立事务边界，必须明确对账责任。

10.1 配额先预留再结算

StorageAccount(teamId,usedBytes,reservedBytes,version) 与 StorageReservation(reservationId,operationId,execSeq,upperBoundBytes,state,leaseUntil) 为唯一计量真源。个人团队照样按 teamId 计，不另开个人配额分支。

外呼/上传前，在 PG 条件更新中保证 used+reserved+requested<=limit 并插入唯一 reservation。未知视频大小按服务端文件上界预留，禁止零预留；下载超过上界必须停止或先扩额。物化完成在同一事务确认真实 bytes、提升 Media 状态、used 增加、reserved 释放；失败进入可重试/取消状态，实际对象回收由持久任务负责。

重复 confirm 对 completed 返回已有结果，不重新加字节、不删除对象。超限拒发生在预留/扩额，不在已收费 finalize 后临时删资产。reservation 过期回收须验证 lease/version，避免回收与晚到 settle 双减。

资金、reservation、intent 与素材写制定统一锁序；保留 TeamBalance→GenerationIntent 的现有方向，网络 IO 全在 DB 事务外。字节算术在 BigInt 域，响应转换显式校验范围。

10.2 幂等分三层

  • 业务身份： 不可变 (sourceIntentRowId,sourceExecSeq,artifactIndex) 对应一次产物；Media 同步唯一约束。可变 NodeArtifact 槽位只表达当前选择，不能代替历史产物身份。
  • 对象身份： 保留当前 deterministic key + 内容 hash，不改回只含 nodeId/intentId 的可覆盖键；put 前有 durable manifest/stage 记录。重试产出不同 hash 是冲突/新结果，不静默覆盖已交付对象。
  • 调度身份： jobId/eventId 辅助去重；removeOnComplete/Failed 后可再次入队，最终幂等依赖 PG 条件与唯一约束。

孤儿 GC 必须查询 manifest、物化租约与已提交引用，删除前再校验，重试清理可追踪。PG 事务不能原子回滚对象存储，因此必须建设这一显式闭环，而不是宣称一个唯一索引就消除了孤儿。

defaultJobOptions 使用完整命名 profile，不依赖 Nest 的嵌套自动合并；运行时断言实际 Queue 的 attempts/backoff/retention。测试针对当前仍存在的队列，不针对已退役 ai-result-download。

10.3 审计与 origin 分离

origin 表记录本地机制：用户、编辑器 binding、UndoManager、provider/connection、服务端命令、维护。不要只列字符串后把 provider 对象误判为表外；Origin.Server 无生产消费的客户端别名可删，真正服务端写 origin 保留。

可信 actor 来自服务端 session/内部认证，auditId 与 traceId 关联命令及持久化批次。DocWriteAudit 或命令事件与内容 delta 同事务提交，避免“有审计无内容/有内容无审计”。高频文本按批次审计连接/作者集合，不每击键额外打一张全量 JSON 表。

用户 per-user origin 不必现在全改，但若未来需要逐字符法律级作者归因，Yjs clientID/origin 不能当可信署名，本批审计只承诺服务器受理者与命令归因。

11. 门禁、不变量与预算

机器化门禁应证明行为与资源上界，而不是只证明符号存在。

11.1 manifest 先行而非最后补门

manifest 作为 TS 单源定义根、类型、创建者、写权限、读出口、撤销责任、持久归属、禁键和转换器；schema 创建、projection、导入/导出与静态门禁从这里消费。读写 census 可做派生检查，但不能声称 AST 能自动知道一个业务字段的语义分类。

新字段未分类构建红；二进制授权、父容器替换、跨代 replay、未知类型、URL 写 exec 等必须有行为门。manifest + 静态扫描不能替代真实网络测试。

11.2 不变量需要对齐 CRDT 并发语义

parent 存在/无环、边端点、storyboard 引用、timeline sourceNodeId、runtime 无节点时不可渲染为独立真源，均写入三列登记：判据、读侧、写侧。

读侧全函数并保留可诊断异常，不修复写回 doc。跨记录强约束由结构命令 actor 保证；客户端并发叶子编辑不能靠“本地检查一次”保证全局无环。execute 另做 topology 数量断言，不能静默跳未知节点。

普通删除后的远端视图按确定规则屏蔽悬空引用；合法维护命令可级联删除，它是业务写，不是投影修复。两者不能被“禁修复写回”混为一谈。

11.3 起步预算与告警

保留 shared 当前 8MiB doc、256KiB 单 update/key、4KiB awareness 作为初始约束，重新验证富文本/最大合法离线 delta 是否与 WS frame 上限一致。节点数先设 10,000；富文本长度、XML 深度和节点数另设上限，不能只看编码字节。

压缩初始触发为 1,000 行或 2MiB 增量或最老增量 60 秒；单项目最短正常压缩间隔 30 秒，超预算可受控提前；全局重放并发 1 起步，按 RSS/事件循环压力限流。读事务 8 秒、短提交事务 5 秒、重放 10 秒为工程上界初值，必须用目标服务器基准调整。

10,000 节点/10 活跃连接压力下拟定验收：单键投影 P95<=16ms、P99<=50ms；稳态事件循环延迟 P99<=50ms；保存屏障 P95<=1s、P99<=3s；冷开当前上限画布 P95<=3s。达不到则降低准入上限或优化粒度，不把数字写成已兑现性能。

Geometry 不设置“同手势最多 K 条修复写”：取消几何派生修复回写，拖拽预览留本地/awareness，手势完成提交 1 次用户几何事务；必要取消/重新绑定按独立命令统计。原 Origin.Geometry 指的是 geometry-repair，并非所有用户拖拽，必须先区分。

A+253B×活节点+15B×累计删除 只保留为某 fixture 的经验描述，不作配额真值。A 由对应 manifest 空文档实测；记录版本、GC 设置、client 数和内容长度。编码字节、JS heap、Undo 保留、XML/文本负载、tombstone 数、快照写放大分别监控。删除项 100,000 或历史残留占编码量超过 30% 且达到 2MiB，进入人工维护候选，不直接自动重建。

指标用尺寸/时延直方图与有限 reason，不把 projectId/nodeId/userId 放 Prometheus 标签。具体项目定位进受权管理视图与采样日志。新增 durable_save_lag、append_gap、generation_fenced、runtime_outbox_oldest_age、storage_reservation_expired、object_gc_pending 等低基数指标。

12. 对 Z1-Z8 的明确处理

  • Z1： 本批整体直接 csv=4、docSchema=4，一次硬切；内部开发里可分阶段构建，不发布 csv4/schema3 的空中间态。数字同值不意味着永久绑定，仍保留“协议/内容”两个独立语义常量。
  • Z2： 选已有项目元数据先获取 g；不采用 localStorage 首连试错。4410 仅处理竞态与真正换代，服务端不信任缓存元数据。
  • Z3： Snapshot 必须含 generation；采用当前代 2 份 + 最近两旧代各最终 1 份的有界起步策略。当前开发数据不回填、不归档搬运。
  • Z4： 连续 3 次不完整告警、关闭破坏性维护并诊断；人工重建仅对已证明完整源执行。不让 identity 命令成为“修复”出口。
  • Z5： origin 机制表 + 服务端可信 actor/command 审计，同 PG delta 事务；不提前做无消费方的 per-user origin，但不把 origin 当安全身份。
  • Z6： 基础后台调度、事务外重放、预算/超时和 bloat 监控随新载体上线；高级频率自适应、分层归档留 Y6。
  • Z7： 不维持 -2a 与 -2b 人为先后部署。manifest/真源→载体与屏障→内容/运行态读者原子改道→配额与测试；最终只发布一个完整 v4 单元。
  • Z8： 保留真实 PG 交错、两浏览器换代及 kill 演练为发布门。当前报告不执行重建；未来实施时用演练库与真实二进制消息证明，不以单测 substitute。

13. 实施顺序与范围重排

内部按承重关系实现，最终以完整 v4 发布，不部署破坏性半成品。

13.1 阶段 A：契约与真源冻结

先交付 manifest、内容/runtime DTO、可信权限模型、generation/session 生命周期和 PG 表约束；将路线图中冲突/过时描述删除而非继续叠加修订。明确 output metadata 不再回写用户 doc，纯文本/富文本与结构撤销责任分开。

13.2 阶段 B：载体与可靠边界

实现连续 appendSeq、generation/epoch fence、snapshot CAS、RR 完整前缀读、后台 compact、保存屏障及本地 flush；随后实现可继续维护状态机与全类型 visible rebuild。每个阶段使用新 schema 演练，不先部署破坏性旧读路径。

13.3 阶段 C：内容与运行态原子改道

Y.Text/XmlFragment 绑定、唯一创建者、bounded undo；exec 出 doc，延伸 PG runtime outbox；全部 data.status/fileId 读者改投影，media refs/复制/公开快照/工作流一起改；删除旧写者与 fallback。不保留双写，也不等待连续 N 天影子双跑；开发阶段使用确定性对拍与故障注入。

结构命令/补偿撤销、节点恢复后的 PG runtime 对齐同时落地。时间轴真实消费迁移不能只建根；不消费的预设新域暂不建。

13.4 阶段 D：配额与对象闭环

外呼前 reservation、幂等 confirm、immutable artifact 身份、对象 manifest/GC、execSeq 退款 fencing、队列配置断言。完善部署 readiness、低基数观测及完整降级矩阵。

13.5 最终发布

所有 P0/P1 门通过后，以明确开发环境为目标重建 DB 和协作缓存，部署 api/web v4；不写 v3→v4 兼容分支、不收养旧无代 spool、不做“快照表 additive 先行+state 暂留”的无需求过渡。未来正式恢复能力保留快照/PITR与维护机器，和现在保护测试存量不是一回事。

回滚当前测试部署可重建回旧测试版本；正式系统内容恢复使用新世代，不把数据库二进制降级和 bundle 回退假称无损回滚。运维脚本对生产环境默认拒绝 reset，防将开发习惯带到正式系统。

14. 必须先红后绿的发布门

以下用例覆盖真实交错、崩溃、违规输入与业务闭环，实施后均须留证。

14.1 持久化与换代

  1. A 取号未提交、B 先提交、compact 与第三读者交错：新协议不能出现前缀缺口，旧无锁水位协议应复现遗漏。
  2. 两 compact 与 append 三方交错：仅一快照发布，append 不丢，指针不回退，CAS 败不删任何行。
  3. 旧代异步 append/spool/内部写在新代切换后到达：数据库原子拒绝；不改标签再重放。
  4. 人为删除增量整行但 pending=null：前缀检测拒载；人为删指针行/改字节：对应 reason 明确。
  5. delete-only 延期数据编码/重放不丢；未解析源不得 visible 重建成功。
  6. 维护每一步 kill：maintenanceId 恢复后既不重复换代，也不开放旧写。
  7. 当前代 compact 与真正 generation rebuild 分别验身份保留/身份刷新；旧 raw update 永不入新代。
  8. 两浏览器、多标签、IDB delete blocked、迟到 callback：正确性不依赖 purge；世代纠偏确实销毁旧 doc。

14.2 保存、文本、撤销与安全

  1. Sync ACK 后、PG 提交前 kill：界面不得先称已保存，本地未确认内容可恢复；PG 屏障 ACK 后 kill，冷启内容完整。
  2. marker 前后的两次编辑、provider batching、重连、旧 nonce：只确认前缀，不能清后续 dirty；delete-only 同样覆盖。
  3. 两端独立同 key 建容器：旧路径先红，新路径创建者唯一，两个后续字段/文本修改均可见。
  4. 100 项剩余 history + 退休项 GC：剩余 undo/redo、嵌套祖先、redone、中文 IME/富文本均正确；200 次结构删除可通过补偿命令恢复有效历史。
  5. 手工二进制写未知根、exec、替换父 map、DeleteSet 删除受保护对象：服务端拒绝，未授权内容不广播。
  6. A 删→B 完成→A undo，A 删→B 退款→A undo，迟到旧生成/退款遇 rearm：无幽灵 loading、无免费交付、无新代误退款。
  7. viewer/匿名/退出团队后叶子与结构命令都拒；单人两标签内容同步且无本人光标浪费。

14.3 runtime、配额与性能

  1. collab kill、Redis 丢队列、运行态通知丢失：PG 当前态恢复 30 秒内可展示；materializing 不假 done。
  2. outbox lease 到期/接管/旧 run mark、同内容但错误状态：不能被“内容等值 fast path”跳过修正。
  3. 两并发 quota reservation/confirm、完成素材重复 confirm：配额不过售、不重复扣字节、不删完成资产。
  4. 同 execSeq 的产物重复 finalize/upload，不同 execSeq rearm：同代无重复 Media，不误吞新代任务，孤儿对象进入可追踪 GC。
  5. reservation 超时与迟到 settle、GC 与新引用交错：计量不负数、对象不误删。
  6. 10,000 节点/10 连接真实文本与媒体负载：测投影、保存、WS event loop、heap、压缩写放大，不能只跑无业务 marker soak。

所有门记录测试载体、故意变红证据、修复提交与发布阻断属性。静态 census 绿、verify 绿和用户体验演练分别记录，不能互相替代。

15. 保留、撤销与最终判断

保留： 单 collab 所有者、Yjs 内容收敛、shared 版本常量、四维缓存键、RR 一致读、PG 计划/执行序、ArtifactCommit 资金原子性、现有 PG poller、服务端权限与版本终态、开发阶段一次硬切原则。

撤销/重写： exec 内自增、exec 进入内容撤销 scope、SV 三守卫作为完整性主证明、无锁 nextval max 水位、identity 世代“修复”、全 pid 缓存强清、仅重建 provider、重建后仍保留旧 Undo 假设、先删 data 字段后补读者、缺 generation 的 snapshot 表、以 jobId 承诺永久 exactly-once。

前移： 最小统一投影、现有富文本协作绑定、结构命令权限、基础 compact 调度/事务外计算、保存屏障与配额预留。仍后置： 批注/高级编辑器、复杂离线结构协同、多实例所有权路由、分层云归档和自动恢复。

最终推荐不是在 Y1c v1 上逐条补守卫，而是在当前已有 PG 权威骨架上，把内容、业务、展示与耐久性边界重新对齐，再一次建设和发布 v4。 这比继续积累版本分支、重连纠偏、双写及撤销补投更小、更可证明，也更符合单人团队与多人团队统一协作的产品目标。
